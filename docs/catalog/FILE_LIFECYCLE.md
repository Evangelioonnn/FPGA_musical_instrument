# 文件生命周期与整理规则

仓库按文件用途管理，不把聊天记录、源码、验证输出和本机缓存混在一起。每次移动文件后必须更新链接，并运行 `python tools/check_repository.py`；Gowin 工程还要重新打开 `.gprj` 检查顶层和文件列表。

## 应长期提交

- 手写 HDL、CST、SDC、`.gprj`、Tcl 构建脚本、仿真 testbench 和必要的离线生成脚本；
- 当前规范、接口契约、角色交接和板卡事实；
- 精选验证摘要、可复现命令、资源/时序报告和用户板测记录；
- 有来源和许可记录的官方资料索引、素材生成说明。

## 只作本机产物

`impl/`、`sim/work*/`、`*.gprj.user`、`*.fs`、`*.bin`、`*.binx`、`*.db`、`*.pr`、临时日志、个人工具缓存、`tmp/` 和 `Notification/` 不进入 GitHub。它们可以保留在本机供下载或排错；完成对应板测且已有哈希/命令记录后再清理。

当前仍可能要下载的固件先不要删除；删除前确认源码和 `build.tcl` 能重建。临时生成的 WAV 只有在它被试听、数值分析或报告引用时才保留到 `evidence/audio/`，否则归入本机缓存。

## 证据和历史

- `evidence/` 只放能说明一个结论的精选输出；原始日志可以按日期归档，但必须在索引中注明“通过项、失败项、未覆盖项”。
- `docs/history/` 保存带日期的规划、会议和被替代的决策；历史内容不覆盖 `docs/project/STATUS.md`。
- 已知失败的 RTL 或构建不直接删除，先标为 `HISTORY_OR_NEGATIVE`，保留失败原因和替代入口；确认没有引用后才可删除。
- 根目录旧说明若只是兼容入口，保留短指针；完整内容放在 `docs/project`、`docs/team` 或 `docs/history`。

## 整理验收

整理任务必须报告：移动/新增/删除清单、链接检查、每个工程的可复现入口、未处理的本机缓存，以及任何仍需用户板测的内容。不得用“目录看起来干净”代替工程重新打开和脚本验证。
