## 2. 音质分析：假设而非诊断结论

信号相关谐波/杂散优先于单纯固定频率底噪：C4约262Hz，若出现约524、786、1048Hz并随着音符同比例移动，可支持非线性失真或确定性数字波形错误；需FFT/记录波形才知道实际频率。仅“听着更尖”不能指定谐波阶数。

| 候选 | 依据与限制 | 下一步证据 |
|---|---|---|
| PT8211低电平转换非线性/过零附近异常 | 单音保持约±256码，约-42dBFS；很低的数字幅度可能使DAC非线性/噪声相对更明显。手册其他供电/测试条件的THD不能直接当本板实测值 | DAC输出的周期波形与谐波，随后与滤波/功放比较 |
| LMV321/NS4263的偏置、增益、失真或耳机负载/检测 | 信号相关失真可随音高走；两副耳机相同不能排除共有驱动级。幅度小也不能仅凭数字值排除模拟工作点问题 | DAC正常但滤波或功放后出现额外低阶谐波/削顶/过零缺口 |
| 实际串行数据或电气时序问题 | 符号位/位对齐/边沿误读会让本来正常的PCM变成周期性失真。RTL检查器与内部STA不等于实物DAC输入验收 | 真实BCK/WS/DIN采样解码；两通道可分步看边沿，完整同时解码最好用≥3数字通道逻辑分析仪 |
| 数字开关与模拟供电/地耦合 | 数据相关耦合可伴随音符，USB/DC对照不能排除板内共有供电与布线影响 | 持续噪声与发声时频谱、模拟地/供电观察，分级定位后再细查 |
| 原音色/查表量化/耳机个体 | 电脑参考接受、两副耳机相同、精度和16/20时钟格式A/B均无改善，使它们作为主要解释的优先级降低 | 不重复盲目更换耳机或音色；保留现有对照结果 |

电脑preview全段统一乘8，播放器和板卡的模拟增益也不同；试听尽量接近响度，不能把播放同样数字文件直接当成声压一致。原方波测试听着正常只证明基本发声，方波自身谐波可能掩盖问题。

当前不调整增益、不添加低通/降噪、不换芯片。若以后需要电平扫描，必须同时管理模拟输出/耳机响度；把数字值调大不等于已经定位问题。

## 3. 明天的最小测量

目标：同一个单音、相同耳机负载下，找到第一处新增明显失真的节点。先用现有16秒演示开头1.2～1.6秒附近的C4保持段；约3.8ms一个周期，避免先测和弦。

已核对的原理图节点（原理图与实物版本仍需确认）：

- DAC左输出：U16/PT8211-S第6脚，HP_LCH。
- 滤波左输出：U17/LMV321第4脚，HP_LCHU。
- 功放左输出：U20/NS4263第5脚，隔直电容C135之前。
- 耳机左输出：C135靠耳机的一端，HP_OUTL。

先CH1测DAC输出、CH2测功放输出；需要时把其中一路移到滤波器输出。芯片1脚方向、实物器件与可靠地参考确认后才落探头；图纸脚号不等于已确认实物可安全夹持位置。

保持耳机插入以维持相同工作模式，但测量时不必戴着。两通道地夹通常共地且接保护地，均接已确认的板卡GND，不能接扬声器负端或NS4263第5脚。高阻输入，探头先×10且仪器设置匹配；先看DC偏置，再看小交流。约1ms/div起步，根据实际幅度调垂直档；不先用平均滤掉尖峰。

记录两点的Vpp、直流偏置、波形、音符、探头/耦合/时基/采样率。FFT可比较262Hz及整数倍峰值，幅度比例需归一化到各自基波；单看屏幕像正弦不能证明没有低幅可闻谐波。DAC采样保持台阶也不能一概判异常。若有导出能力保存原始采样，若有逻辑分析仪再抓三根数字线。

DAC处已有异常：向串行接收、DAC工作点、供电继续查；DAC干净而后级异常：查对应模拟级。这个分支不能单凭一次肉眼观察定案。

## 5. 先约定三个边界

- 输入到核心：note_on/note_off、0..127音符号、力度0..256、valid/ready。松键必须对应按下时的音符身份，尤其换八度/切模式后；溢出、断线不能挂音。
- 参数到核心：参数ID、范围/单位、更新时机、应答/实际值、本地与蓝牙冲突策略。第一版建议正在操作的本地控件优先，远程命令有明确应答，此规则待三人确认。
- 核心到反馈：held、occupied（含尾音）、踏板、当前参数、peak/clip；快音频不能等待慢屏幕/蓝牙。反馈建议先20～50Hz快照，具体实现预算后定。

现有 `project/expression/INTERFACES.md` 是可参考的已实现候选接口，不代表UART/BLE、输入队列、仲裁或外接显示已经实现。`expression_baseline`只是本轮固定音色试听顶层，仪表输出尚未接成真实反馈（其中部分固定为0）；C不能把这些固定值当成实时测量。正式集成时明确音色保持原基准，其他音色单独实验。

IO数量、方向、电平、总线与供电预算先约定；真实针位/Bank/CST必须查资料并实测核对，音频功能未全部完工也可并行做需求表。PCB发出前再冻结接口。

## 6. GitHub建议操作流程（本轮仅讨论）

当前目录未建Git。三人初心者建议GitHub Desktop管理日常操作，各自使用自己账号和本地克隆。一人维护仓库，两位Collaborators，不共用账号。建议私有仓库，暂不创建。

早先曾建议main/develop/feature三级；本次建议先简化为main＋短期feature分支，三人确认后采用。main表示可复现、已完成所声明检查，已知板卡噪声必须写明；不冒称主分支已整机验收。需要长期并行集成时再引入develop。

建库当天顺序：

1. 三人安装Git/GitHub Desktop，登录各自账号；确认同一器件版本、Gowin版本和可用仿真命令。安装路径可不同，公共脚本路径参数化，本机设置不提交。
2. A整理现有目录，先写排除规则，再检查待提交文件；建立首次源码提交和可复现说明，发布为私有GitHub仓库。B/C克隆同一个仓库，而非下载ZIP作为长期副本。
3. 提交源码、波表/初始化数据、CST/SDC、gprj、Tcl、仿真脚本/测试、接口文档、团队自产的PCB源文件和简要报告。保留baseline依赖的instrument/expression共享源目录，不能只上传单个gprj。
4. 排除impl、ModelSim工作库、波形缓存、gprj.user等本机状态；不提交软件安装包、个人许可证/凭据、大量官方PDF。官方资料保存来源/版本/校验，需离线共享时另设资料包。实际ignore规则建库时检查后再写，不能按后缀误排除手写或必要生成的HDL/ROM。
5. 重要fs/WAV/报告作为某个源码commit/tag对应的里程碑产物保存（例如Release附件），附文件哈希、工具版本、时序/资源、板测状态；日常不把整个impl文件夹来回提交。

每次任务：

1. 确认当前工作已提交/妥善保存，在Desktop切main→Fetch origin→Pull，得到统一起点。
2. 从最新main创建任务分支，例如 `feat/input-matrix`、`feat/ble-volume`、`fix/audio-path`，一次只做一个可验收功能。
3. 仅改负责目录，在自己的电脑仿真/测试。Commit写清具体变化，Push到远程，再Create Pull Request，目标main。
4. PR写明接口版本、改动、验证命令/结果、是否真正上板、剩余问题。A检查接入与顶层；A自己的修改由另一人复核。顶层/CST/SDC改动集中由A合并。
5. 目标分支有新修改时，用Desktop的Update from main（或合并main）更新任务分支；冲突由相关负责人逐段解决，不能直接全部采用某一侧。相关测试通过后合并PR。
6. 合并后，其他人在自己的本地main重新Fetch/Pull。仍有工作的功能分支再合并新main，不覆盖未提交的改动；下个任务使用新分支。

Commit只存本机，Push把该分支上传，PR请求评审，Merge并入main，Pull获取远端变化；Push功能分支不会自动更改别人电脑，也不会自动合并main。

Git只同步已提交文件，不同步三人的对话。每轮协作先给当前分支/commit、负责目录、接口版本、任务和验收条件，读PROJECT_CONTEXT/开发约定/对应接口文档；结论回填各任务交接记录。多人或多个会话不同时改同一份工作目录/分支；需要时另开分支与独立工作副本。

建议新目录（建库时再创建）：`hardware/interaction/`归B；`project/input/`按A/B约定；`project/communication/`、`project/visual/`、`host/`归C；共享接口文档与整机顶层归A集成。不复制三份音频核心让队友各改一份。

特别记录本次GUI故障：Pull或外部编辑改变gprj文件列表后，关闭再打开Designer，确认正确顶层。仿真/构建必须从同一源码commit复现，不能只传一个无法追溯来源的fs。
